# 七维审查清单（§3）

> **单一表述约定**：「六层审查顺序」是七维清单的**优先级视图**（L1–L6 按阻断性排序，L6 风格对应第①维），不是另一套清单。全文只用「七维清单」，六层表仅作执行顺序使用。

> 本文件由 `SKILL.md` 按需加载；`§N` 编号与原单文件版一致（对照表见 `SKILL.md`）。

## 三、Layer 2: 代码审查（七维清单）

> **核心理念**：Self-Review 先行；读测试优先；数据流追踪；反馈可执行。

### 3.1 审查顺序（两遍法 + 4 步）

**两遍法**（吸收自 senior code review 实践：设计对不对 → 细节对不对）：

- **Pass 1 设计遍**：这是正确的方案吗？与现有架构/模式一致吗？能不能更小？——发现问题立即反馈，不读完全部细节再推翻（先读 PR 描述与 diff 文件列表定影响面）
- **Pass 2 细节遍**：在 Pass 1 无结构问题的前提下，按 §3.4 六层顺序走

**细节遍 4 步**：

1. **读测试代码** → 理解预期行为（tests reveal intent better than implementation）
2. **读实现代码** → 验证测试覆盖度；bug 修复必须配回归测试，否则视为未完成
3. **正向数据流追踪** → input → validation → business logic → persistence → response
4. **反向追踪** → external call → validation → business logic → side effect

**审查测试的附加要求**（Review the Tests, Not Just the Code）：

- 新增行为必须有"没有修复就会失败"的测试，不是恰好与修复一起通过的测试
- 警惕测试剧场：断言实现细节（mock 一切、检查内部调用次数）的测试，重构时全部失效却抓不住任何行为
- 错误路径和边界必须测，不只测 happy path

### 3.2 Self-Review 四问（提交前自查）

1. **可读性**：命名清晰？逻辑直白？需注释？
2. **边界/异常**：空值、超时、并发、资源泄漏是否处理？
3. **测试**：正常/异常/边界三类覆盖？达标？
4. **重复**：可提取公共代码？遵循 DRY？

### 3.3 反馈质量

**可执行反馈四要素**：位置（文件:行号）→ 问题（具体描述，不主观评价）→ 建议（给方案或参考）→ 依据（链接规则/文档）。

**Conventional Comments 标注体系**（吸收自 conventionalcomments.org，机器可解析）：

```
<label> [decorations]: <subject>

[discussion]
```

| label | 用途 | 默认阻断性 |
|-------|------|-----------|
| `issue` | 指出具体缺陷 | 默认阻断；`(non-blocking)` 装饰可解除 |
| `suggestion` | 改进提议，须说明 why | 默认阻断，`(non-blocking)`/`(if-minor)` 可解除 |
| `nitpick` | 琐碎偏好 | 恒不阻断 |
| `question` | 不确定是否为问题时用 | 恒不阻断 |
| `todo` | 小而必要的修改 | 不阻断 |
| `praise` | 指出做得好的地方 | —（每份审查至少留 1 条真实 praise） |
| `chore` | 正式接受前的流程任务 | 视流程而定 |

装饰：`(non-blocking)` 不阻止接受 · `(blocking)` 阻止接受 · `(if-minor)` 改动轻微时才需处理 · 领域装饰如 `(security)` `(perf)` `(test)`。每条评论最多 1-2 个装饰，多则失去可读性。

**禁止**：模糊（"这里不好"）、情绪化（"太烂了"）、主观（"我觉得…"）。

**审查时效**：≤24h 首次反馈；>48h 阻塞升级（换审查人/简化范围）。

**审批策略**：关键模块（安全/支付/核心业务）2 人审批 + CI 全绿；一般模块 1 人；紧急修复快审事后补。

### 3.4 七维审查清单

**执行顺序视图（L1–L6，七维清单按阻断性重排；L6 风格 ↔ 第①维，L5 可维护性 ↔ 第⑥维）**：

| 层 | 维度 | 判定标准 | 阻断性 |
|---|------|---------|--------|
| L1 | 正确性与边界 | 行为符合意图；空值/边界值/异常输入/并发/数据一致性；off-by-one；幂等重放 | 命中即 P0/P1 |
| L2 | 安全性 | §3.4④ OWASP 清单；凭据硬编码；输入验证；auth/authz 中间件在位 | 命中即 P0 |
| L3 | 可靠性 | 错误处理不裸吞；资源释放；超时在位；失败模式有降级 | 命中即 P1 |
| L4 | 性能 | N+1；循环内大对象操作；无界查询；阻塞主流程；缺分页 | 视影响 P1/P2 |
| L5 | 可维护性 | DRY；模块边界；循环依赖；配置外部化；向后兼容 | P2 |
| L6 | 风格与文档 | 命名一致性；魔法数字；注释 why-not-what；文档同步 | P3，恒不阻断 |

- 风格/格式类问题一律由工具（lint/format）拦截，人工审查不产出 P3 级格式意见（对齐 GitLab「风格自动化强制，而非审查评论」）
- 每层完成后再进下一层；L1/L2 命中 P0 可提前终止后续层（早停门，§1.1）

#### ① 可读性与风格

- 命名清晰一致（camelCase/snake_case/PascalCase 统一）
- 函数 ≤50 行；嵌套 ≤3 层（超标 → Guard Clause/提前返回）
- 消灭魔法数字/硬编码值 → 提取常量
- 注释解释 why 而非 what，必要且准确
- 条件表达式不复杂化（可读的布尔提取）

**Bug 分析三分离原则**（吸收自缺陷定位工作流方法论）：
- **事实与推测分离**：问题描述只写"观察到什么"，禁止出现"可能是""应该是"。已确认现象须有日志/截图/SQL 结果直接证明。
- **现象与根因分离**：无日志/数据支撑的结论一律标注"待验证假设"，禁止无证据断言根因。根因分析必须解释防线为何失效，基于时间线/实验/证据链。
- **测试与回归分离**：回归范围必须三级清单（必测 P0 链路 / 建议测关联模块 / 抽测低关联），禁止模糊写"相关功能"。

#### ② 架构原则

**SOLID**：S 单一职责（一类一事）；O 对扩展开放对修改关闭；L 子类可替换父类；I 接口小而专；D 依赖抽象不依赖实现。

**补充原则**：
- **DRY + YAGNI**：无重复代码、无过度设计、删除不需要的功能
- **关注点分离**：业务逻辑/数据访问/UI 分层合理，不过度抽象也不抽象不足

#### ③ 测试覆盖

- 主要逻辑路径 + 边界条件（空值/边界值/异常输入）+ 错误路径均有测试
- 测试独立、可重复，命名清晰描述场景
- 无脆弱测试（依赖外部状态/时间/顺序）
- Mock/Stub 使用合理，不过度 mock

**回归分级清单**（三分离原则之测试与回归分离）：
- **必测（P0 链路）**：直接受影响的业务路径，修复后必须 100% 通过
- **建议测**：关联模块，可能受波及，按优先级执行
- **抽测**：低关联，概率较低场景，随机抽样验证
- 禁止只写"相关功能要回归"等模糊表述

**覆盖率门禁**：

| 类型 | 阈值 |
|------|------|
| 新增代码单元测试 | ≥ 80% |
| 分支覆盖率 | ≥ 70% |
| 关键路径（支付/认证/核心业务） | 100% |
| API 契约测试 | 覆盖所有 endpoint |
| E2E 用户主流程 | 覆盖 5-10 个核心场景 |

#### ④ 安全性（OWASP Top 10 + 补充）

**OWASP Top 10 检查**：

| 编号 | 风险 | 检查点 |
|------|------|--------|
| A01 | 访问控制 | 用户权限正确验证 |
| A02 | 加密失效 | 敏感数据加密存储和传输 |
| A03 | 注入攻击 | SQL 参数化查询；命令注入安全处理；XSS 输出转义 |
| A04 | 不安全设计 | 业务逻辑无安全漏洞 |
| A05 | 安全配置 | 无不安全默认配置 |
| A06 | 组件漏洞 | 依赖无已知漏洞（SCA 扫描） |
| A07 | 认证失败 | 认证逻辑健壮 |
| A08 | 完整性故障 | 数据完整性验证 |
| A09 | 日志监控 | 安全事件有记录 |
| A10 | SSRF | 用户提供的 URL 安全处理 |

**补充检查**：敏感信息硬编码（Key/密码/Token）→ 环境变量；错误信息不泄露内部实现细节；CSRF 防护；文件上传安全（类型/大小/路径校验）；速率限制防滥用；.env/.pem/.key 等敏感文件不入库。

#### ⑤ 性能

- 算法时间复杂度合理，无不必要的循环/重复计算
- 数据库查询优化：N+1 问题、缺索引
- 无内存泄漏风险（大对象、未释放资源、无限缓存增长）
- 大数据量分页/流式处理
- 缓存合理使用（命中率/失效策略）
- 异步正确处理，无阻塞主流程的操作
- 网络请求有 timeout（对应语言规则 PY-10/GO-04/JS-06）

#### ⑥ 可维护性

- 模块划分合理，依赖清晰，无循环依赖
- 错误处理完善：异常正确捕获、有意义错误消息、不裸吞
- 日志充分便于排查（结构化，含 trace_id）
- 配置外部化（环境变量/配置文件），支持多环境
- 易于扩展修改，API 设计合理、向后兼容

#### ⑦ 企业就绪度与运维成熟度

- **错误处理与日志**：结构化日志（JSON：level/timestamp/trace_id/span_id），错误信息不泄露内部实现
- **配置管理**：所有敏感配置外部化，支持 dev/staging/prod 多环境
- **灾难恢复**：有备份策略、回滚方案、RTO/RPO 定义
- **可观测性**：日志+指标+链路追踪三支柱齐全，SLO 定义清晰
- **CI/CD 自动化**：流水线覆盖代码检查/构建/测试/部署；lockfile 强制提交
- **部署与回滚**：部署时间可量化、回滚流程标准化、灰度发布机制
- **监控告警**：告警阈值合理、噪声控制、分级响应
- **文档完整性**：README/API 文档/ADR 定期更新
- **数据架构**：实体关系清晰、事务一致、迁移版本兼容可回滚、无范式违规、数据流可追踪
