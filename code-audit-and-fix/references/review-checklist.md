# 七维审查清单（§3）

> **单一表述约定**：「六层审查顺序」是七维清单的**优先级视图**（L1–L6 按阻断性排序，L6 风格对应第①维），不是另一套清单。全文只用「七维清单」，六层表仅作执行顺序使用。

> 本文件由 `SKILL.md` 按需加载；`§N` 编号与原单文件版一致（对照表见 `SKILL.md`）。

## 三、Layer 2: 代码审查（七维清单）

> **核心理念**：Self-Review 先行；读测试优先；数据流追踪；反馈可执行。

### 3.0 反合理化表（Do Not Skip，来源 trailofbits/skills differential-review，2026-10-27 吸收）

> 审查动作被跳过的理由往往是下面这些「合理化借口」。**每个借口都有对应反例与强制动作**——出现借口即触发强制动作，不允许「这次特殊」。

| 借口 | 为什么错 | 强制动作 |
|---|---|---|
| "改动很小，快速过一下" | Heartbleed 只有 2 行 | **按风险分级，不按行数**（§3.0.1 风险触发器） |
| "这个库我很熟" | 熟悉滋生盲点 | 显式建立基线上下文（架构/约定/调用方）再下结论 |
| "git 历史太费时" | 历史暴露回归（被删的安全检查/降级的校验） | 高风险文件必跑 `git blame` / `git log -L` |
| "影响面一眼就看得出来" | 会漏传递调用方 | 高风险变更**量化计算**影响面（调用方 grep + 依赖图） |
| "没测试不是我的问题" | 缺测试 = 风险放大 | 在报告中标注缺口并**上调该发现的级别**（P2→P1） |
| "只是重构，无安全影响" | 重构会破坏不变量（参数求值时机/副作用顺序/异常路径） | 重构默认按高风险审，直到证明无害 |
| "口头说明发现就行" | 无落盘产物 = 发现丢失 | 报告必须写文件/落报告模板（§9.2），逐条可引用 |

**适用边界**：本表约束的是**跳过审查步骤**的倾向；不约束「按档位裁剪范围」（轻量档本就跳过语义组，那是成本决策不是合理化）。

#### 3.0.1 风险分级触发器（与三路分发联用）

| 风险 | 触发器 | 审查动作 |
|---|---|---|
| 高 | auth / crypto / 外部调用 / 资金转移 / 校验逻辑被删 / 凭据处理 | 完整流程：W1+W2+数据流追踪+blast radius+对抗分析 |
| 中 | 业务逻辑变更 / 状态机修改 / 新增公共 API | W1+W2，跳过对抗分析 |
| 低 | 注释 / 测试 / UI 文案 / 日志 | W1 静态组即可 |

**代码库规模策略**（吸收 trailofbits：SMALL/MEDIUM/LARGE 三档）：≤20 文件全量深读（含依赖与 git blame）；20-200 文件重点审高风险文件+一跳依赖；>200 文件只走关键路径（P0 链路+高风险触发器命中者）。

### 3.0.2 不报反清单（精度优先，来源 alibaba open-code-review「precision over noise」取舍 + Anthropic「verified then posted」口径，2026-10-27 吸收）

> 审查的价值 = 报出的问题里真缺陷的占比（Precision）。**宁可少报，不可虚报**——大量误报会让作者开始跳过审查意见，审查从此失效。以下类型**默认不报**：

| 不报项 | 理由 | 例外（必须报的情形） |
|---|---|---|
| 纯格式/风格（缩进、引号、import 排序） | lint 工具职责（既有铁律：L6 风格交工具） | 格式掩盖了逻辑（如用缩进伪造块结构） |
| 「可以更优雅」的无缺陷实现 | 不是缺陷是品味，作者有权选择 | 该实现已在代码库其他处被约定否定 |
| 未经证实的性能担忧（「可能慢」） | 无测量即无缺陷（收益数字禁进决策依据，宿主 architecture.md） | 有边界输入量的证据（如无界查询+已知数据量级） |
| 与本次 diff 无关的既有问题 | Pre-existing，混报稀释信噪比（§1.3 增量去重） | P0 且修复成本一行以内（顺手修+标注） |
| 纯假设的边界（「如果传 NaN 会怎样」而调用链上不可能出现 NaN） | 虚构不可达路径 = 噪声 | 该函数是导出 API，调用方不可控 |
| 建议引入新依赖/新抽象「以防将来」 | YAGNI（宿主 codegen.md 第 1 阶梯） | 已存在 ≥3 处重复代码且已标 `code_clone` |
| 注释/文档的措辞偏好 | P3 级品味 | 文档与行为矛盾（文档在「撒谎」） |

**反清单的维护**：作者对某类意见反复点踩/驳回 ≥3 次 → 该类意见进项目级反清单（落宿主 `CODE_REVIEW_CHECKLIST.md` 的项目段），本技能不存储项目状态。

### 3.0.3 防假阳性三原则（来源 alibaba/loongcollector code-review skill 原文，2026-10-27 吸收）

1. **分析问题时必须包含充分上下文，不能只看局部 diff 就下结论**——先读变更函数、调用方、定义处，再判问题（与 W2 数据流追踪衔接：孤立 hunk 不出 P0/P1 结论）
2. **结论必须基于实际读取到的代码与变更，不允许基于记忆或猜测**——引用的每一处证据必须带 `file:line` 且当轮实际读过（与 B1 证据门槛同源）
3. **先理解作者意图和端到端流程，再给出问题判断**——先产出「意图理解」（作者要解决什么/改了哪些关键路径/影响哪些模块），再进问题列表；跳过意图直接报问题 = 把有意设计报成缺陷

### 3.1 审查顺序（两遍法 + 4 步）

**两遍法**（吸收自 senior code review 实践：设计对不对 → 细节对不对）：

- **Pass 1 设计遍**：这是正确的方案吗？与现有架构/模式一致吗？能不能更小？——发现问题立即反馈，不读完全部细节再推翻（先读 PR 描述与 diff 文件列表定影响面）
- **Pass 2 细节遍**：在 Pass 1 无结构问题的前提下，按 §3.4 六层顺序走

**细节遍 4 步**：

1. **读测试代码** → 理解预期行为（tests reveal intent better than implementation）
2. **读实现代码** → 验证测试覆盖度；bug 修复必须配回归测试，否则视为未完成
3. **正向数据流追踪** → input → validation → business logic → persistence → response
4. **反向追踪** → external call → validation → business logic → side effect

**审查测试的附加要求**（Review the Tests, Not Just the Code）：

- 新增行为必须有"没有修复就会失败"的测试，不是恰好与修复一起通过的测试
- 警惕测试剧场：断言实现细节（mock 一切、检查内部调用次数）的测试，重构时全部失效却抓不住任何行为
- 错误路径和边界必须测，不只测 happy path

### 3.2 Self-Review 四问（提交前自查）

1. **可读性**：命名清晰？逻辑直白？需注释？
2. **边界/异常**：空值、超时、并发、资源泄漏是否处理？
3. **测试**：正常/异常/边界三类覆盖？达标？
4. **重复**：可提取公共代码？遵循 DRY？

### 3.3 反馈质量

**可执行反馈四要素**：位置（文件:行号）→ 问题（具体描述，不主观评价）→ 建议（给方案或参考）→ 依据（链接规则/文档）。

**Conventional Comments 标注体系**（吸收自 conventionalcomments.org，机器可解析）：

```
<label> [decorations]: <subject>

[discussion]
```

| label | 用途 | 默认阻断性 |
|-------|------|-----------|
| `issue` | 指出具体缺陷 | 默认阻断；`(non-blocking)` 装饰可解除 |
| `suggestion` | 改进提议，须说明 why | 默认阻断，`(non-blocking)`/`(if-minor)` 可解除 |
| `nitpick` | 琐碎偏好 | 恒不阻断 |
| `question` | 不确定是否为问题时用 | 恒不阻断 |
| `todo` | 小而必要的修改 | 不阻断 |
| `praise` | 指出做得好的地方 | —（每份审查至少留 1 条真实 praise） |
| `chore` | 正式接受前的流程任务 | 视流程而定 |

装饰：`(non-blocking)` 不阻止接受 · `(blocking)` 阻止接受 · `(if-minor)` 改动轻微时才需处理 · 领域装饰如 `(security)` `(perf)` `(test)`。每条评论最多 1-2 个装饰，多则失去可读性。

**禁止**：模糊（"这里不好"）、情绪化（"太烂了"）、主观（"我觉得…"）。

**审查时效**：≤24h 首次反馈；>48h 阻塞升级（换审查人/简化范围）。

**审批策略**：关键模块（安全/支付/核心业务）2 人审批 + CI 全绿；一般模块 1 人；紧急修复快审事后补。

### 3.4 七维审查清单

**执行顺序视图（L1–L6，七维清单按阻断性重排；L6 风格 ↔ 第①维，L5 可维护性 ↔ 第⑥维）**：

| 层 | 维度 | 判定标准 | 阻断性 |
|---|------|---------|--------|
| L1 | 正确性与边界 | 行为符合意图；空值/边界值/异常输入/并发/数据一致性；off-by-one；幂等重放 | 命中即 P0/P1 |
| L2 | 安全性 | §3.4④ OWASP 清单；凭据硬编码；输入验证；auth/authz 中间件在位 | 命中即 P0 |
| L3 | 可靠性 | 错误处理不裸吞；资源释放；超时在位；失败模式有降级；**弱依赖有降级预案**（黄山版设计规约【强制】7） | 命中即 P1 |
| L4 | 性能 | N+1；循环内大对象操作；无界查询；阻塞主流程；缺分页 | 视影响 P1/P2 |
| L5 | 可维护性 | DRY；模块边界；循环依赖；配置外部化；向后兼容 | P2 |
| L6 | 风格与文档 | 命名一致性；魔法数字；注释 why-not-what；文档同步 | P3，恒不阻断 |

- 风格/格式类问题一律由工具（lint/format）拦截，人工审查不产出 P3 级格式意见（对齐 GitLab「风格自动化强制，而非审查评论」）
- 每层完成后再进下一层；L1/L2 命中 P0 可提前终止后续层（早停门，§1.1）

#### ① 可读性与风格

- 命名清晰一致（camelCase/snake_case/PascalCase 统一）
- 函数 ≤50 行；嵌套 ≤3 层（超标 → Guard Clause/提前返回）
- 消灭魔法数字/硬编码值 → 提取常量
- 注释解释 why 而非 what，必要且准确
- 条件表达式不复杂化（可读的布尔提取）

**Bug 分析三分离原则**（吸收自缺陷定位工作流方法论）：
- **事实与推测分离**：问题描述只写"观察到什么"，禁止出现"可能是""应该是"。已确认现象须有日志/截图/SQL 结果直接证明。
- **现象与根因分离**：无日志/数据支撑的结论一律标注"待验证假设"，禁止无证据断言根因。根因分析必须解释防线为何失效，基于时间线/实验/证据链。
- **测试与回归分离**：回归范围必须三级清单（必测 P0 链路 / 建议测关联模块 / 抽测低关联），禁止模糊写"相关功能"。

#### ② 架构原则

**SOLID**：S 单一职责（一类一事）；O 对扩展开放对修改关闭；L 子类可替换父类；I 接口小而专；D 依赖抽象不依赖实现。

**补充原则**：
- **DRY + YAGNI**：无重复代码、无过度设计、删除不需要的功能
- **关注点分离**：业务逻辑/数据访问/UI 分层合理，不过度抽象也不抽象不足
- **弱依赖识别**（黄山版设计规约【强制】7）：系统设计须准确识别弱依赖并针对性设计降级与应急预案——审查时核对「这个依赖挂了核心功能还在吗」的答案落在代码而非口头

#### ③ 测试覆盖

- 主要逻辑路径 + 边界条件（空值/边界值/异常输入）+ 错误路径均有测试
- 测试独立、可重复，命名清晰描述场景
- 无脆弱测试（依赖外部状态/时间/顺序）
- Mock/Stub 使用合理，不过度 mock

**回归分级清单**（三分离原则之测试与回归分离）：
- **必测（P0 链路）**：直接受影响的业务路径，修复后必须 100% 通过
- **建议测**：关联模块，可能受波及，按优先级执行
- **抽测**：低关联，概率较低场景，随机抽样验证
- 禁止只写"相关功能要回归"等模糊表述

**覆盖率门禁**：

| 类型 | 阈值 |
|------|------|
| 新增代码单元测试 | ≥ 80% |
| 分支覆盖率 | ≥ 70% |
| 关键路径（支付/认证/核心业务） | 100% |
| API 契约测试 | 覆盖所有 endpoint |
| E2E 用户主流程 | 覆盖 5-10 个核心场景 |

#### ④ 安全性（OWASP Top 10 + 补充）

**OWASP Top 10 检查**：

| 编号 | 风险 | 检查点 |
|------|------|--------|
| A01 | 访问控制 | 用户权限正确验证 |
| A02 | 加密失效 | 敏感数据加密存储和传输 |
| A03 | 注入攻击 | SQL 参数化查询；命令注入安全处理；XSS 输出转义 |
| A04 | 不安全设计 | 业务逻辑无安全漏洞 |
| A05 | 安全配置 | 无不安全默认配置 |
| A06 | 组件漏洞 | 依赖无已知漏洞（SCA 扫描） |
| A07 | 认证失败 | 认证逻辑健壮 |
| A08 | 完整性故障 | 数据完整性验证 |
| A09 | 日志监控 | 安全事件有记录 |
| A10 | SSRF | 用户提供的 URL 安全处理 |

**补充检查**（对齐阿里 Java 开发手册（黄山版）安全规约【强制】项 + OWASP 补充，2026-10-27 吸收）：

- 敏感信息硬编码（Key/密码/Token）→ 环境变量；**配置文件中的密码需加密**（黄山版 10）→ 密文槽/`ENC_`（宿主 `security.md` 凭据分级处置）
- 错误信息不泄露内部实现细节
- **用户敏感数据展示前脱敏**（黄山版 2）；日志中的敏感信息脱敏（黄山版 14）
- **文件上传：大小/类型/路径严格校验**（黄山版 9）
- **平台资源防重放**（短信/邮件/下单/支付：数量限制+疲劳度控制+验证码）（黄山版 8）
- **表单/AJAX 提交 CSRF 验证**（黄山版 6）；HTML 输出转义防 XSS（黄山版 5）
- **用户输入参数一律有效性验证**（黄山版 4：page size 上限、order by 白名单、防 SSRF/重定向）
- **用户个人页面/功能权限校验（水平越权）**（黄山版 1）；URL 外部重定向白名单（黄山版 7）
- SQL 一律参数绑定，禁止字符串拼接（黄山版 3，与 PY-14/JAV-04 同源）
- 速率限制防滥用；.env/.pem/.key 等敏感文件不入库（UNIV-01）

> 黄山版安全规约共 11 条（10 强制 + 1 推荐），本清单按主题并入口——**命中即 P0**（与 OWASP 各项同权重），规约原文以《Java开发手册（黄山版）》为准，本表只做审查视角的并集复述。

#### ⑤ 性能

- 算法时间复杂度合理，无不必要的循环/重复计算
- 数据库查询优化：N+1 问题、缺索引
- 无内存泄漏风险（大对象、未释放资源、无限缓存增长）
- 大数据量分页/流式处理
- 缓存合理使用（命中率/失效策略）
- 异步正确处理，无阻塞主流程的操作
- 网络请求有 timeout（对应语言规则 PY-10/GO-04/JS-06）
- **远程调用必须有超时设置**（黄山版服务器规约【强制】1，与 PY-10 同源；超时生效顺序以客户端方法级 > 接口级 > 服务端为准）
- **慢服务隔离线程池**（黄山版【推荐】：独立线程池隔离慢服务，避免拖垮主线程池）

#### ⑥ 可维护性

- 模块划分合理，依赖清晰，无循环依赖
- 错误处理完善：异常正确捕获、有意义错误消息、不裸吞
- 日志充分便于排查（结构化，含 trace_id）
- 配置外部化（环境变量/配置文件），支持多环境
- 易于扩展修改，API 设计合理、向后兼容

#### ⑦ 企业就绪度与运维成熟度

- **错误处理与日志**：结构化日志（JSON：level/timestamp/trace_id/span_id），错误信息不泄露内部实现
- **配置管理**：所有敏感配置外部化，支持 dev/staging/prod 多环境
- **灾难恢复**：有备份策略、回滚方案、RTO/RPO 定义
- **可观测性**：日志+指标+链路追踪三支柱齐全，SLO 定义清晰
- **CI/CD 自动化**：流水线覆盖代码检查/构建/测试/部署；lockfile 强制提交
- **部署与回滚**：部署时间可量化、回滚流程标准化、灰度发布机制
- **监控告警**：告警阈值合理、噪声控制、分级响应
- **文档完整性**：README/API 文档/ADR 定期更新
- **数据架构**：实体关系清晰、事务一致、迁移版本兼容可回滚、无范式违规、数据流可追踪

#### ⑧ 并发与生命周期（v4.0 新增维度，来源 loongcollector code-review 评估标准「并发与生命周期」组）

> 定位：七维之外的**专项 overlay 维度**——不改变「七维清单」称谓与 L1-L6 顺序视图，仅在高风险档（并发代码/资源管理/后台任务命中时）启用，审查动作挂靠 W2 语义组。

- **线程/锁/队列**：锁粒度是否恰当；**锁顺序是否跨模块一致**（多模块各自加锁顺序不一致 = 死锁源）；数据竞争（共享可变状态有无保护）；线程能否安全退出并被回收
- **异步/回调**：回调链上的竞态与悬空引用；异步失败路径是否被处理（对应 JS-07/GO-01 的语义面）；新增后台任务/定时器是否有**可控停止机制**（对应 PY-11 裸线程）
- **资源释放闭环**（每条路径逐一核对，不是只看 happy path）：启动失败 / 热更新替换 / 正常删除 / 进程退出——四条路径下线程、连接、文件句柄、队列消费者都能收干净
- **状态恢复正确性**：重载/回滚后是否回到「一致可用」状态，而非半更新（部分组件恢复、部分残留旧态）；失败回滚时旧实例是否保持可用
- **生命周期 verdict**（高风险档必输出，三态 PASS/FAIL/未验证 + 各附 1-3 条证据）：资源释放 · 死锁/卡死风险 · 状态恢复正确性——写进报告「后置核验」段（§9.2）

### 3.5 规约三级映射（来源阿里 Java 开发手册（黄山版）分级体系，2026-10-27 吸收）

> 黄山版用【强制】【推荐】【参考】三级标注每条规约。本技能 P0-P3 与之建立稳定映射，避免同一缺陷在两套体系里级别漂移：

| 黄山版 | 本技能 | 说明 |
|---|---|---|
| 【强制】 | P0 或 P1 | 安全类强制 → P0；健壮性/资源类强制（如远程调用超时）→ P1 |
| 【推荐】 | P2 | 建议修复，本 PR 或转 follow-up |
| 【参考】 | P3 | 作者自行决定 |

**映射约束**：只映射**方向**，不逐条照搬——黄山版是 Java 手册，其【强制】在本技能语言规则库（§6）已有对应规则号的（如配置密码加密 ↔ PY-07 家族）以规则号为准；无对应规则号的按本表方向定级，**不为黄山版新增语言规则号**（§6 是 40 项闭集）。
