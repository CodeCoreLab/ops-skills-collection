## 二、Layer 1: 依赖与上下游核验

> **核心理念**：SemVer 是信号不是证明；lockfile 是契约不是文档；SBOM 是资产不是报告。

### 2.1 依赖审查（每次引入/升级必查）

**SemVer 契约**：MAJOR 升级必查 changelog + 跑回归 + 验证契约 + 备回滚方案；MINOR 检查向后兼容；PATCH 仍需验证；内部私有包不豁免。

**Lockfile + SBOM**：必须提交 git，禁止入 .gitignore；CI 强制 lockfile 一致（`npm ci` / `install --frozen-lockfile` / `poetry install --no-interaction`）；CycloneDX/SPDX 格式纳入流水线；传递依赖审查（`npm ls --all` / `pipdeptree`）。

**主版本升级 4 要素**：影响范围清单 → 破坏性变更映射 → 回滚方案 → 测试/预发灰度 24h 再生产。

**Dependabot/Renovate 审查 4 步**：读 changelog → 本地全量测试 → 影响面分析 → 接口契约验证。

### 2.2 上游调用前核验（契约前置）

- **Schema 契约**：OpenAPI 定义 → 字段名/类型/必填/枚举/边界值；序列化一致性；用 client gen，避免手写 DTO 与 server 不一致
- **认证授权**：token 时效、权限 scope、限流阈值
- **幂等性**：重试安全（GET/PUT/DELETE 天然幂等；POST 需 Idempotency-Key）
- **SLA/SLO + 环境一致性**：P50/P99 响应时间、降级行为约定；开发/测试/生产配置 diff
- **错误码契约**：HTTP 状态码 + 业务错误码映射，客户端覆盖全部错误码

### 2.3 下游调用后核验（数据一致性后置）

- **响应契约**：字段完整、类型正确、值域合规（如百分比 0-100）
- **数据一致性**：Write-after-read 验证 → DB → 缓存 → 消息队列状态；分布式事务边界、补偿机制
- **幂等重放**：重复请求结果一致（尤其写操作）
- **缓存一致性**：失效策略（write-through/behind）、TTL 合理性；消息投递语义（至少/至多/恰好一次），消费端幂等

**契约对称性**：请求侧与响应侧 schema 双向可验证，任一方变更需通知另一方（消费者驱动契约测试，Pact）。

### 2.4 整体健康评分（量化基线）

**双维度量化评分**：整体健康分 1-10 + 维度评分 1-5 加权汇总。

| 维度 | 权重 | 评分标准（1-5） |
|------|------|----------------|
| 结构完整性 | 20% | SOLID 合规、模块边界清晰、无循环依赖、无上帝类(>500 行) |
| 安全边界 | 20% | OWASP 无高危、凭据安全、输入验证、依赖 CVE 扫描 |
| 可扩展性 | 15% | 支撑 10x 增长、无单点故障、无硬编码限制 |
| 性能与成本 | 15% | 无 N+1/内存泄漏、缓存合理、无阻塞操作 |
| 企业就绪度 | 15% | 错误处理、日志、配置外部化、DR/回滚、可观测性 |
| 运维成熟度 | 10% | CI/CD 自动化、部署时间可量化、监控告警、文档完整 |
| 数据架构 | 5% | 事务一致、迁移兼容、无范式违规、数据流清晰 |

**评分锚点**：5=行业最佳无需改进；4=良好轻微优化；3=可接受有已知技术债；2=需关注影响扩展；1=严重阻碍业务。

**健康等级**：

| 总分 | 等级 | 处置 |
|------|------|------|
| 8-10 | 健康 🟢 | 正常迭代 |
| 6-7 | 亚健康 🟡 | 技术债可控，Sprint 内规划 |
| 4-5 | 警告 🟠 | 需专项治理 |
| 1-3 | 危险 🔴 | 阻塞业务，冻结新功能先还债 |

**证据强制**：每项评分必须引用具体 `文件:行号` + 代码片段/指标数据支撑，禁止主观判断；标注 N/A 须说明理由。

## 四、Layer 3: 架构与重构

### 4.1 分层与依赖方向（严格单向）

```
UI (Controller/Handler)
    ↓
Service (Business Logic)
    ↓
Repository (Data Access)
    ↓
Infrastructure (DB/HTTP/MQ)
```

**治理**：严禁反向依赖（Domain 不 import UI）；严禁跨层调用（UI 不直访 Repository）；端口/适配器解耦（Hexagonal）；DI 容器管理生命周期。

### 4.2 微服务原则

| 原则 | 含义 | 反例 |
|------|------|------|
| Database-per-service | 每服务独立 DB，禁跨库 JOIN | 多服务共享一个 DB |
| Shared-nothing | 无共享状态，独立部署 | 共享内存/文件/Redis |
| API-first | 先定契约后写实现 | 先写代码后补 API |
| Event-driven | 异步事件解耦 | 同步 RPC 强耦合 |
| Observability Day 1 | 日志+指标+链路追踪从第一天起 | 事后补监控 |

### 4.3 坏味道识别与重构时机

| 坏味道 | 触发阈值 | 重构方向 |
|-------|---------|---------|
| 过大函数 | >50 行 | Extract Method |
| 过长参数 | >4 个 | Parameter Object |
| 过深嵌套 | >3 层 | Guard Clause |
| 过宽异常捕获 | except Exception / except: | 精确异常类型 |
| 重复代码 | >3 处 | Extract Common |
| 死代码 | 未引用/未使用 | 删除 |
| 全局可变状态 | 模块级 dict/list/set | 依赖注入 |
| 循环依赖 | import 环 | 接口抽象/依赖倒置 |
| 违反单一职责 | 一类多事 | 拆分模块 |

### 4.4 可观测性

每服务必备：结构化日志（JSON：level/timestamp/trace_id/span_id）、指标（Counter/Gauge/Histogram）、链路追踪（OpenTelemetry + W3C TraceContext）。SLO：可用性 99.9%+、延迟 P95/P99、错误率 <0.1%。

### 4.5 架构决策记录（ADR）

四段式：Context（背景）→ Decision（决策）→ Consequences（后果）→ Alternatives（拒绝的方案及理由）。存放 `docs/adr/0001-xxx.md`，永久保留。

### 4.6 重构 ROI 决策矩阵

| 影响 \ 难度 | 低 | 高 |
|------------|-----|-----|
| **高** | 立即执行 | 规划后分批执行 |
| **低** | 顺手做（Boy Scout） | 暂缓或放弃 |

量化：影响面（文件数/调用者/业务关键性）× 难度（改动行数/依赖复杂度/测试成本）。

### 4.7 7R 现代化框架（吸收自代码健康度评估模板）

**组件级战略决策矩阵**（避免一刀切重写论）：

| 策略 | 含义 | 适用场景 | 成本 |
|------|------|---------|------|
| **Retain** 保留 | 不改，继续用 | 无风险、成本低、已稳定 | 无 |
| **Refactor** 重构 | 改代码结构 | 业务不变，质量提升 | 低 |
| **Rehost** 重托管 | 换运行环境 | 云迁移 | 中 |
| **Replatform** 换平台 | 用新平台能力 | 用 PaaS 特性（如托管 DB） | 中 |
| **Repurchase** 采购 | 换成品 | 自建成本 > 采购成本 | 高 |
| **Rewrite** 重写 | 从头写 | 遗留系统不可救（罕见） | 高 |
| **Retire** 退役 | 淘汰 | 已废弃功能、无调用者 | 低 |

**应用规则**：
- 优先 Retain/Refactor，**Rewrite 是最坏选项**（90% 遗留系统不需要重写）
- 每个组件给 7R 推荐 + 理由，禁止"全重写"论
- 与 §4.6 ROI 矩阵联动：ROI 高 + Refactor 可行 → 立即执行；ROI 低 + Refactor 成本高 → Retain 观察
- **禁止**：以"技术债高"为由建议 Rewrite（应先量化 ROI）

### 4.8 变更放大系数（CAC）

**定义**：Change Amplification Coefficient = 每功能修改文件数 / 功能复杂度

**健康基准**：3-5 个文件 / 功能

| CAC | 状态 | 处置 |
|-----|------|------|
| <5 | 健康 🟢 | 架构解耦良好 |
| 5-10 | 警告 🟡 | 关注热点模块 |
| 10-20 | 危险 🔴 | 耦合严重，专项治理 |
| >20 | 崩溃 🔥 | 架构失控，需重构 |

**计算方法**：从 git log 分析最近 50 次提交的平均文件修改数；或人工评估典型功能的跨文件改动范围。

**联动指标**：CAC 高 + Bus Factor 低（§5.5）= 架构风险极高，优先治理。
