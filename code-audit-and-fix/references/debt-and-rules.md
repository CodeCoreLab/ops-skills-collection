## 五、Layer 4: 技术债治理

> **核心理念**：债务可量化、可决策、可配额。生命周期：识别 → 量化 → 记录（关联行号）→ 决策 → 修复 → 验证（重新审计）→ 关闭。

### 5.1 DICE 评分（严重度量化）

- **D**（部署频率）×3 + **I**（集成难度）×4 + **C**（变更失败率）×2 + **E**（用户影响）×1
- 分数越高越优先修复（D/I 权重最高，直接影响迭代效率）

### 5.2 ROI 决策

```
ROI = (月损工时 × 12 × 人力费率) / (修复工时 × 人力费率) - 1
```

| ROI | 决策 |
|-----|------|
| < 0 | 暂缓 |
| 0-2 | 低优先级，Sprint 尾部 |
| 2-5 | 中优先级，下个 Sprint |
| > 5 | 立即修复 |
| > 10 | Sprint 优先，团队级 |

### 5.3 质量门禁（未达则 CI fail）

覆盖率 ≥80%（新代码）· 重复率 ≤3% · 静态分析 A 级 · 0 高危漏洞（SAST/SCA）· 0 类型错误 · 格式化 100%。

**TDR（技术债比率）**：目标 5%，报警 15%，超阈值冻结新功能先还债。

### 5.4 配额与六分类

Sprint 容量 15-20% 给技术债；Boy Scout 规则每次修改让代码好一点。

| 类别 | 例子 | 策略 |
|------|------|------|
| 代码债 | 重复/复杂逻辑/坏味道 | 小步重构、SOLID |
| 测试债 | 缺测试/脆弱测试 | 补测试、隔离外部依赖 |
| 文档债 | README/API 文档过时 | 定期更新、代码即文档 |
| 基础设施债 | 老框架/缺监控 | 渐进升级、补可观测性 |
| 认知债 | 只有作者懂/命名混乱 | 结对审查、文档沉淀 |
| 集成债 | 手动集成/无 CI/CD | 自动化流水线 |

**债务清单模板**：

| 类别 | 描述 | DICE | ROI | 优先级 | 状态 |
|------|------|------|-----|--------|------|
| 测试债 | 核心模块无单元测试 | 12 | 15.0 | Sprint 优先 | 进行中 |

### 5.5 巴士因子与知识债（吸收自代码健康度评估模板）

**Bus Factor（巴士因子）**：唯一掌握某模块的负责人数（Bus = 1 表示只有 1 人懂，此人离职/生病即失联）。

**高风险信号**：
- 关键业务逻辑只有 1 人能 review 通过
- 代码中出现"只有 X 懂"的口头流传
- 频繁出现"这个只能问 X"的情况
- 模块变更历史集中在单一作者（git blame 单点）

**修复策略**：
- **强制 ADR**：所有架构决策走 §4.5 ADR 流程
- **结对代码**：Bus Factor = 1 模块强制结对开发
- **轮值负责人**：关键模块设置主备负责人，Bus Factor ≥ 2
- **文档沉淀**：每月技术债回顾会议，关键逻辑强制注释
- **Code Review Checklist**：强制覆盖，降低知识集中度

**知识债量化**：统计所有模块的 Bus Factor 分布，Bus Factor = 1 的模块占比 >30% 视为高风险。

## 六、语言扫描规则库（40 项 = PY 18 + GO 7 + JAV 4 + JS 7 + UNIV 4）

**扫描原则**：只做精确模式匹配（`re.MULTILINE`），不做模糊推断。

**硬编码密钥三条防漏/防误报约束**（2026-10-26 实测校准）：
1. 必带 `(?i)` 不区分大小写——`API_KEY` / `ApiKey` / `SECRET` 是主流写法，大小写敏感必漏
2. 值长阈值 `{8,}`：过滤 `key = "id"` 类误报，真实密钥/令牌几乎不会短于 8 字符
3. 命中后仍需人工确认是否为占位符（`"xxx"`、`"your-key-here"`、`""`）：属占位符则降 P2 并建议改为环境变量读取
4. B 形态模在 `tests/`、`fixtures/`、`examples/`、`*.md` 里命中 → 默认按 P2 并标注「疑似测试数据」；仅当值形似真实生产令牌且同文件无 teardown 清理时才升 P0（2026-10-26 实测：credvault 32 个 py 文件扫出 1 条，位于 `tests/test_smoke.py` 的 fixture，属 P2）

### Python（18 项）

| 编号 | 缺陷 | 规则 |
|------|------|------|
| PY-01 | 裸 except | `except\s*:` 或 `except\s+Exception\s*:` |
| PY-02 | 无意义异常吞没 | `except\s+(\w+)?\s*:\s*pass` |
| PY-03 | 可变默认参数 | `def\s+\w+\s*\([^)]*=\s*(\[\]|\{\}|set\(\))` |
| PY-04 | 循环内字符串拼接 | `(\+=\s*f?"[^"]*"|re.match.*)\s*for\s+` |
| PY-05 | 全局可变对象 | 模块级 `^[a-z_]+\s*=\s*(\[\]|\{\})` |
| PY-06 | subprocess shell=True | `subprocess\.[a-zA-Z]+\s*\([^)]*shell\s*=\s*True` |
| PY-07 | 硬编码密钥 | **双模，任一命中即报**<br>**A 关键字模**：`(?i)(password|passwd|secret|token|key|api|access_key|private_key|credential)\s*[:=]\s*["'][^"']{8,}["']`<br>**B 形态模**：值本身带已知令牌前缀/结构 → `["'](sk-[A-Za-z0-9_-]{10,}|sk_live_[A-Za-z0-9]{10,}|ghp_[A-Za-z0-9]{20,}|gho_[A-Za-z0-9]{20,}|xox[baprs]-[A-Za-z0-9-]{10,}|AKIA[0-9A-Z]{12,}|AIza[0-9A-Za-z_-]{20,}|-----BEGIN [A-Z ]*PRIVATE KEY-----)["']`<br>**为什么必须双模**：A 模靠变量名，命名自由时必漏——2026-10-26 实测 `API = "sk-live-9f8e…"` 在 A 模下漏报，B 模按 `sk-` 前缀命中。<br>**必带 `(?i)`**：`API_KEY`/`ApiKey` 惯用大写，大小写敏感必漏。<br>**`{8,}` 值长阈值**：过滤 `key = "id"` 类误报。 |
| PY-08 | 明文密码存储 | `password\s*=\s*["'][^"']+["']`（非加密上下文） |
| PY-09 | HTTP 禁用验证 | `verify\s*=\s*False` |
| PY-10 | 无 timeout 请求 | `requests\.(get|post|put|delete|patch)\s*\([^)]*\)` 且无 `timeout=` |
| PY-11 | 裸线程/进程创建 | `threading\.Thread\(`/`multiprocessing\.Process\(` |
| PY-12 | 未关闭资源 | `open\(`/`sqlite3\.connect\(` 未配 `with` 或 `try/finally` |
| PY-13 | pickle 反序列化外部数据 | `pickle\.load\(`/`pickle\.loads\(` |
| PY-14 | SQL 字符串拼接 | `execute\s*\(\s*(f["']\|["'][^)]*["']\s*%\|\["'][^)]*["']\s*\+)\|execute\s*\([^)]*\.format\s*\(`<br>**2026-10-27 修正**：原式 `execute\s*\(\s*[f""'].*%s\|[f""'].*\.format` 漏报**最常见的 f-string 拼接**（`conn.execute(f"INSERT ... {x}")`）——`.format` 分支能命中但 f-string 分支要求同行出现 `%s`，实跑案例 1 的 L7 漏报。改为「execute 后紧跟 f-string / % 拼接 / + 拼接 / .format」四形态；参数化写法 `execute(sql, params)` 与 `execute("...?", (x,))` 均不命中（已实测） |
| PY-15 | 弱哈希算法 | `md5\s*\(` 或 `sha1\s*\(`（密码/签名场景） |
| PY-16 | 字典链式 get | `.get\([^)]+\)\.get\(` |
| PY-17 | 异常中 print 而非 log | `except.*:\s*print\s*\(` |
| PY-18 | import * | `import\s+\w+\s*\*` |

## 七、缺陷分级与测试要求

| 级别 | 标签 | 含义 | 修复要求 | 阻断合并 | 注释前缀 |
|------|------|------|---------|---------|---------|
| **P0 阻塞** 🔴 | BLOCKER | 安全漏洞、数据丢失风险、生产故障、正确性 bug | 立即修复，禁止合并 | ✅ | 🚨 **issue (blocking):** |
| **P1 强制** 🟡 | REQUIRED | 严重逻辑错误、异常缺失、资源泄漏、SLA 违约 | 本轮必须修复 | ✅ | **issue (blocking):** |
| **P2 优化** 🟢 | SUGGESTED | 代码重复、命名不规范、复杂度超标、非关键路径测试缺口 | 建议修复，本 PR 或建跟踪 issue | ❌ | **suggestion:** |
| **P3 参考** 🔵 | OPTIONAL | 风格建议、文档补充、命名品味 | 可选，作者自行决定 | ❌ | **nitpick:** |

**判定细则**：
- 安全类（PY-07/08/09/13/14/15、GO-05/06、JAV-03/04、JS-01/02/03/04/05、OWASP 各项命中）→ **P0**
- 资源类（PY-11/12、GO-02/03/04、JS-06/07）+ 逻辑类（PY-01/02/03/04/05、GO-01、JAV-01/02）→ **P1**
- 规范类（PY-16/17/18 等）→ **P2** 或 **P3**

**分级呈现铁律**（对齐 software-code-review skill）：P0/P1 与 P2/P3 **分组呈现，不混在同一个列表**；阻断性问题与可选项的边界必须清晰，禁止让一个优先级淹没另一个。

**分级轴与标签轴正交（§10）**：P0-P3 回答「多急」，修复标签（噪声/冗余/重复/结构/可靠性）回答「怎么改」。每条发现须同时给出级别 + 标签 + 主动词，标签不改变级别。40 项规则 → 标签/动词的归口映射表见 `fix-taxonomy.md` §10.4（唯一权威源，本文件不重复）。

**根因判定约束**（三分离原则之现象与根因分离）：
- 无日志/SQL/调用链证据支撑的结论一律标注"待验证假设"，禁止断言根因
- 根因分析必须解释"防线为何失效"，基于时间线+实验+证据链
- 无复现条件或反驳实验时，只能写候选原因，不能写最终根因

**测试生成原则**：
- P0 修复 → 必须新增攻击向量测试
- P1 修复 → 必须有异常路径测试
- 重构 → 更新现有测试确保行为不变
- 新功能 → 正常 + 边界 + 异常三类测试
- 异步代码 → `pytest-asyncio`，覆盖超时/取消/重试
- **等价重构类修复**（噪声/冗余/重复/结构）→ 补「行为不变」回归测试；**可靠性类修复** → 补「原缺陷复现 → 修复后消失」的测试

### 7.5 T-shirt 工作量估算

**四档估算**（禁止写"稍等"、"大约"等模糊表述）：

| 尺寸 | 工时 | 场景 |
|------|------|------|
| **S** | <4 小时 | 单文件小改动、命名规范、注释补充 |
| **M** | 1-2 天 | 跨文件修改、单模块重构 |
| **L** | 3-5 天 | 跨模块重构、技术债专项 |
| **XL** | >1 周 | 架构级改造、跨服务重写 |

**判定依据**：文件数 × 复杂度 × 测试成本 × 依赖数量。禁止估算时不考虑依赖影响面。

**联动**：T-shirt size + DICE 评分（§5.1）+ ROI（§5.2）→ 综合决策修复优先级与排期。
