# 执行流程细则（§1）

> 本文件由 `SKILL.md` 按需加载；`§N` 编号与原单文件版一致（对照表见 `SKILL.md`）。

## 一、执行流程（两阶段 × 三路分发 × 并行分组）

**层次原则**：先判定能否批准（阻断层），再深入可选项（优化层）。对齐 Google 审查标准："确定是整体改进即可批准，不追求完美"——阻断层有 P0 即早停输出，可选项不阻塞结论。

### 1.1 执行顺序（三阶段 + 按需修复阶段）

```
阶段 A · 阻断判定（串行，快速通道）
  A1: 确定范围 → 全量 / Git 变更 / 代码片段
  A2: 分发判定 → 轻量/标准/对抗；片段模式跳过依赖核验（§2）
  A3: 自动扫描 → 40 项规则（§6）中阻断类规则优先（P0/P1 类）
  ⛔ 早停门：扫出 P0 → 立即输出阻断报告，跳过阶段 C（用户明确要求全量时除外）

阶段 B · 深度审查（并行分组，见 §1.2）
  W1（静态规则组）‖ W2（语义分析组）‖ W3（Spec 忠实轴，有需求上下文时）
  → 汇聚集合：去重 + 置信度标注（§1.3）

阶段 C · 优化与报告（仅无 P0/P1 时完整执行；有 P0 时仅生成阻断报告）
  C1: 性能/可维护性/测试覆盖细化 → §3.4 ⑤⑥③
  C2: 技术债量化（DICE/ROI）+ 健康评分 → §2.4/§5
  C3: 生成报告 → §9.2 模板
  C4: 覆盖声称自检 → §1.4.2 三项可点回 + 独立 critic 位；无 critic 位则走 §1.4.3「不完整」终态

阶段 D · 自动修复（用户说「自动修复/清理死代码/去冗余/消除重复」时）
  D1: 打标签 + 定动词 → §10.2 / §10.3（fix-taxonomy.md）
  D2: 过滤 → §10.5 三张表（可自动 / 待人工 / 禁止自动）
  D3: 自动堆逐点改 + §10.6 四项验证（单批 ≤10）
  D4: 人工堆出方案不改码 → §10.8 双视角报告
```

**核心框架**：阻断判定（先）→ 并行深审（中）→ 优化/技术债（后）→ 自动修复（按需）。P0/P1 修复后必走验收循环：修→最小验证→≤3 轮回修→升级人工。

### 1.2 并行分组与依赖关系

| 分组 | 检查项 | 可并行原因 |
|------|--------|-----------|
| **W1 静态规则组**（工具化，互不依赖） | 40 项规则 grep · 敏感文件/lockfile 检查 · 循环依赖/上帝类扫描 · 依赖版本扫描 | 纯模式匹配，只读文件内容，无相互依赖 |
| **W2 语义分析组**（互不依赖，可并行） | 正向数据流追踪 · 逆向数据流追踪 · OWASP 清单过查（§3.4④）· 测试覆盖评估 | 各自独立成结论，结论互不为输入 |
| **W3 Spec 忠实轴**（独立子代理，可并行） | 对照原始需求/spec/issue 逐条核对实现忠实度：功能是否齐全 · 是否夹带未要求改动 · 是否偏离约定行为 | 独立上下文，只接收 diff + 原始需求，**不接收 W1/W2 结果**——避免确认偏误（来源 mattpocock/skills code-review 双轴：Standards 与 Spec 并行互不污染，2026-10-16 吸收） |
| **串行依赖**（必须后置） | 缺陷分级 → 去重聚合 → 技术债量化（DICE/ROI 以问题清单为输入）→ 报告生成 | 每步以上一步产出为输入 |

**发现者与验证者分离**（finder ≠ verifier，来源 Cloudflare security-audit-skill「The agent that checks a finding is never the agent that found it」，2026-10-27 吸收）：

- **同一会话上下文里发现的 P0/P1 候选，不得由同一上下文自我确认**——发现者上下文里全是「它为什么是真的」的推理，让它验证自己 = 确认偏误
- **验证方式（按规模二选一）**：① 可派子代理时：把候选问题 + 文件范围交给**全新上下文**的验证者，任务只有一个——**证伪**（找「它其实是误报」的证据，如上游中间件已校验、调用方有前置条件）；② 无法派子代理时：**清空当前推理链**，只带「候选问题 + 相关源码」重新走一遍判定，写明验证时的上下文边界
- 与 B1 证据门槛的关系：B1 要求「P0/P1 上报前给最小证明」，本条规定「证明的动作必须由不带发现者偏见的上下文执行」——**验证者的任务是推翻候选，推翻失败才算 confirmed**
- `needs_validation` 状态：验证者推翻不了也确认不了（缺执行环境、缺上游代码）→ **降级为待验证假设，不给严重度**（Cloudflare 口径：needs_validation 不带 severity，防止「懒得追就给个 medium」）
- **验证计划可证伪（inconclusive 停住）**（来源 lemon-bug-analyser，2026-11-23 吸收）：P0/P1 候选进入验证前必须写下三个字段——**prediction**（"若真有此缺陷，跑 X 必看到 Y"）、**pass_if**（什么观察结果坐实缺陷）、**fail_if**（什么观察结果排除缺陷）。只有 pass_if 没有 fail_if 的验证 = 找一个能证明自己的样本，不算验证。验证执行后出现第三种结果——**该采的字段没采到**（查了另一个时间窗、抓包没带 trace id、环境不匹配）——必须标 **inconclusive 停住等补采**，禁止模糊成"疑似/待验证"，更禁止无声降级为 confirmed。与三态判定衔接：inconclusive 归入"待验证"组，但必须写明"差哪一次补采、谁来补"。

### 1.3 聚合规则

- 同一 `文件:行号` 被多项检查命中 → **保留最高级别**，规则引用合并（如 `PY-07 + OWASP-A02`）
- W1 命中但 W2 无法语义确认 → 降级标注"待验证假设"（对齐 §三 三分离原则），不定级 P0
- W3 Spec 轴发现「夹带改动/偏离需求」类问题单独归类，不与 Standards 轴缺陷合并去重（两轴发现的问题类型正交）；Spec 轴报「缺功能」时标注来源 `[spec]`
- **候选问题的三态判定**（来源 Cloudflare security-audit-skill 三 verdict，2026-10-27 吸收；取代单一「待验证假设」标注）：
  | 状态 | 判定 | 允许的级别 |
  |---|---|---|
  | **确认** | 有完整源码追溯（从触发点到危险点的代码路径）+ 有界观察结果（测试/探针/日志） | P0-P3 任意 |
  | **待验证** | 有精确疑点但缺一步关键证据（写明卡在哪个未决事实） | **不给 P0/P1**，只入「待验证」组 |
  | **已否定** | 验证者找到反驳证据（上游已校验/架构上不可达/误报形态） | **仍要记录**——「查过且没问题」≠「没查过」，否定留档防止下轮重复报 |
  - 三态描述**证据链进度**，不是严重度：确认=证据闭环，待验证=证据缺一环，已否定=证据反驳
  - 已否定不静默丢弃：报告尾部列「本轮已否定候选」清单（一句话+理由），供下轮增量审查去重
  - **被否定的「安全缺口」必查纵深防御**：缺 Layer B 校验但 Layer A 已拦截 → 记「加固建议」不记漏洞（Cloudflare：「纵深防御缺口不是漏洞，是加固项」）
- 每条发现标注置信度：**高**（grep 直击 + 上下文确认 + 验证者未推翻）/ **中**（单引擎命中）/ **低**（待验证态）
- 分级对齐 §7：阻断类（P0/P1）与可选项（P2/参考）在报告中**分组呈现，不混线**
- **打标签（阶段 B 汇聚时必做）**：每条发现额外标一个 §10 标签（24 标签闭集）+ 主动词（10 动词闭集）；级别定严重度、标签定动作，两者互不替代；同位置多标签按 §10.9 仲裁
- **增量审查去重**（来源 Anthropic Claude Code review pipeline「59% 的重复标记指向首审就存在的代码」，2026-10-27 吸收）：复审/增量审查时，对非本次 diff 引入的问题标 `Pre-existing`（预先存在）并分组呈现，不与本次引入的问题混计；同一问题上一轮已报且代码未改 → 不重复上报，只引用前轮编号

### 1.4 指纹、覆盖声称与终态（v4.2.0 新增，来源 Cloudflare security-audit-skill 一手仓库，2026-11-24 吸收）

> 来源文档 → `~/.workbuddy/ondemand/security-audit-workflow-design.md` §J1–J5。本节只落可执行判据。

#### 1.4.1 指纹跨状态稳定（取代「文件:行号」作跨轮 dedup 主键）

同一根因在不同轮次、不同 verdict、不同级别下必须是**同一指纹**，一份记录。

```
指纹 = <模块/子系统> :: <根因形态> :: <被违反的不变量>
例：auth::jwt-signature-skip::verify_before_decode
    api/handlers::unauth-tenant-read::owner_binding_absent
```

- **禁止**指纹含：行号、波次、agent 名、级别、verdict。任一出现即失效（一次重构/一次重分级就变成新指纹，已否定清单重复报）
- 行号保留在发现正文里，**不进指纹**
- 旧口径兼容：既有报告的 `文件:行号` 仍可作**定位**，但跨轮对账以指纹为准

#### 1.4.2 覆盖声称须由账本 + 独立 critic 位证明

**覆盖结论不是一句「已审过」。** 报告里的覆盖声称必须能逐条点回三项：

| 项 | 要求 |
|---|---|
| 哪个检查项 | 规则号／维度（§3.4 ①②…⑧）／OWASP 编号 |
| 哪些路径 | 实际 Read 过的文件清单（不是「模块名」） |
| 谁跑的 | 主 Agent 还是某子代理；独立 critic 位是否指认过缺口 |

- **禁止**用「审了 N 个文件」「派了 3 个 agent」作覆盖证据——agent 数量不是证据
- **独立 critic 位**：覆盖缺口必须由**未参与该片审查的调用位**指认（子代理优先；单会话时清空推理链重走一遍并声明边界）。没有独立 critic 位，**禁止**写「无遗留问题」「覆盖完整」「已全面审查」
- 独立 critic 的产物是「缺口清单」，不是「finding 清单」——它发现的是没审到的地方，不是新漏洞

#### 1.4.3 四终态，禁中途停

审查只有两条合法终点，不存在第三条：

| 终态 | 条件 |
|---|---|
| **完整** | 全部报告产物写出 + 分级/标签/指纹校验通过 + 覆盖账本缺口闭合 |
| **不完整** | `incomplete` + **确切 reason**（预算耗尽／critic 未跑／候选未验完／目标超出可审范围） |

- `incomplete` 的缺口披露位置是**报告首段**，不是脚注、不是收尾栏
- 禁止：审了一半按完整口径写报告；预算不够就悄悄缩范围；候选没验完却说「无 P0」
- 与 `core.md §固定版式消息截断` 同向：只削可变段，头尾固定段（含缺口声明）完整保留

#### 1.4.4 rejected 只压单条主张，不冻结文件

- `已否定` 抑制的仅是「**同一条**失败主张 + 证据未变」；源码或证据一变即为新工作，须重审
- 前轮 `已完成覆盖` 的单元只贡献证据与优先级，**不贡献「其余没问题」**
- 判据：**被否定的主张 = 范围**，不是「被否定的文件 = 范围」。已否定清单腐化成永久豁免清单是本机制最常见的失效形态

**验收循环（P0/P1 修复后必走）**：

```
修复 → 最小验证 → 通过 → Step 9 后置核验
              └→ 不通过 → 回修（≤3 轮）→ 3 轮仍不过 → 停止盲改，回溯根因，升级人工
```

- **验证方式（对应修复目标的最小验证）**：P0 安全漏洞 → 攻击向量测试通过；P1 异常处理 → 异常路径测试 exit 0；脚本修改 → `py_compile` + 最小路径实跑；配置/部署 → 产物打开 + 服务 restart 后探活
- **禁止**：验证不通过却报"已修复"；第 3 轮后继续盲改（回溯根因优先于重试）
- **报告标注**：未闭环的修复在总结中单独列出，不混入"已修复"计数

## 二、接收审查侧（被审者如何处理审查意见）§1.5

> 现有流程只有「审查方」（怎么发现问题）；本节是「接收方」（拿到意见怎么办），来源 obra/superpowers `receiving-code-review`（2026-10-27 吸收）。适用于：本技能产出报告后作者侧的处理，以及本技能作为代理被他人 review 时。

**核心原则**：技术核验，而非情绪表演。收到意见先核验真伪，再决定采纳或反驳——**绝不**表演性附和（"You're absolutely right!" 类），**绝不**不核验就改码。

**六步流程**（每条意见独立走完）：

```
READ → 读完整条意见（含装饰与规则引用），不确定的先停下问，不先改易懂的后问难的
UNDERSTAND → 重述需求：这条意见要求行为变成什么样
VERIFY → 对照代码现实核验：读意见指向的 file:line + 调用方 + 测试，判断「对本代码库技术上正确吗？会破坏现有功能吗？」
EVALUATE → 三选一：采纳 / 反驳（给技术理由+证据）/ 部分采纳（说明边界）
RESPOND → 采纳的直接改；反驳的回「不同意的理由 + 证据（代码/测试/调用链）」
IMPLEMENT → 一次一项、每项配验证；完成后回「Fixed. <file:line>」不写道歉与客套
```

**分诊规则**：

| 意见类型 | 处置 |
|---|---|
| 事实错误（意见指的问题不存在） | 反驳 + 证据，不礼貌性接受 |
| 真缺陷 | 走 §B4 验收循环修复 |
| 与宿主规则冲突（如意见要求引入宿主禁止的依赖/抽象） | 以宿主规则为准，回指针说明 |
| 「正规实现」类建议（上框架/加抽象层） | **先 YAGNI 核验**：grep 实际调用方，无人消费 → 提议不引入（对齐 `rules/codegen.md §Ponytail`） |
| 模糊意见（「这里不好」「再优化一下」） | 要求具体化（哪个行为、什么场景），不猜测改码 |
| 超范围意见（指向本次变更外的既有问题） | 转 follow-up，不扩大本次范围（与 §1.3 Pre-existing 分组一致） |

**与三态判定的闭环**：接收方反驳成功的意见 → 回写到审查方的「已否定候选」清单（§1.3），形成双向核验记录。

---

**阻断判定与批准规则**（吸收 Google eng-practices + GitLab code review 指南）：

- **批准标准**：确定是代码库的整体改进即可批准，不因"不完美"拒绝——可选项（P2/参考）不阻塞结论
- **阻断红线**：P0/P1 存在即不批准；正确性/安全性/设计劣化必须修复；无测试守护的高风险新行为必须补测
- **早停输出**：P0 扫出后立即给出阻断报告（结论 + 位置 + 证据 + 修复方向），不等待优化层完成；用户要全量报告时再走阶段 C
- **不阻断清单**（对齐 software-code-review skill 的 "When Not to Block"）：纯 P3 风格偏好、可写得更"漂亮"但无缺陷的实现、影响范围外的既有问题（转 follow-up issue 不扩大本次范围）、作者已明确接受并跟踪的低风险测试缺口
- **必须阻断清单**：P0/P1、数据迁移/公共 API 形态/安全边界的破坏性变更、合并后修复代价高昂的事项

**审查收敛控制**（来源 Anthropic Claude Code 团队：曾出现单 PR 50+ 轮评审不收敛的失控案例，2026-10-27 吸收）：

- **回修轮次上限 3 轮**（与验收循环一致）；复审改为 **diff-only**（只看新改动，不整 PR 重扫）
- 审查者对同类问题**报类不报行**：第一次发现某类缺陷时给类级描述（如「本 PR 有 3 处裸 except，均判 P1」），后续同位不再逐行重报
- **收敛门**：连续 2 轮评审无新增 P0/P1 → 视为收敛，剩余 P2/P3 转 follow-up
- 审查意见本身也接受复审：人对审查评论点踩/驳回的记录，沉淀为该项目的「误报模式」，下次审查前置排除（宿主 `CODE_REVIEW_CHECKLIST.md` 承接团队侧积累，本技能不存储项目级状态）

**Fresh-context 原则**（来源 Anthropic Claude Code review pipeline + Anthropic best practices「verification subagent with fresh model tries to refute」，2026-10-27 吸收）：

- **审查者上下文必须独立于实现者上下文**：审查 diff 的会话不携带「实现时的推理过程」（设计争论、废弃的尝试、自我辩护）——这些会把早期决策当约束，漏掉隔离状态下显而易见的问题
- 落地方式：W1/W2/W3 各自独立上下文已是本技能既有设计；本条新增要求——**汇聚者（定级+去重的人/代理）只读发现清单 + 必要源码**，不回读各组的完整推理链
- 上下文预算：审查者加载的上下文 = 项目约定（宿主清单）+ diff + 受影响函数的完整源码；**不加载**：实现会话历史、前几轮评审的完整推理（只加载其结论清单）

**三路分发（审查深度自动分流）**：

| 级别 | 触发条件 | 审查内容 | 预期深度 |
|------|---------|---------|---------|
| 轻量 | 改动 <100 行，无敏感标签 | 静态规则扫描 + 快速人工（跳过 W2 语义组） | 快通道，1 轮 |
