# 执行流程细则（§1）

> 本文件由 `SKILL.md` 按需加载；`§N` 编号与原单文件版一致（对照表见 `SKILL.md`）。

## 一、执行流程（两阶段 × 三路分发 × 并行分组）

**层次原则**：先判定能否批准（阻断层），再深入可选项（优化层）。对齐 Google 审查标准："确定是整体改进即可批准，不追求完美"——阻断层有 P0 即早停输出，可选项不阻塞结论。

### 1.1 执行顺序（三阶段 + 按需修复阶段）

```
阶段 A · 阻断判定（串行，快速通道）
  A1: 确定范围 → 全量 / Git 变更 / 代码片段
  A2: 分发判定 → 轻量/标准/对抗；片段模式跳过依赖核验（§2）
  A3: 自动扫描 → 40 项规则（§6）中阻断类规则优先（P0/P1 类）
  ⛔ 早停门：扫出 P0 → 立即输出阻断报告，跳过阶段 C（用户明确要求全量时除外）

阶段 B · 深度审查（并行分组，见 §1.2）
  W1（静态规则组）‖ W2（语义分析组）‖ W3（Spec 忠实轴，有需求上下文时）
  → 汇聚集合：去重 + 置信度标注（§1.3）

阶段 C · 优化与报告（仅无 P0/P1 时完整执行；有 P0 时仅生成阻断报告）
  C1: 性能/可维护性/测试覆盖细化 → §3.4 ⑤⑥③
  C2: 技术债量化（DICE/ROI）+ 健康评分 → §2.4/§5
  C3: 生成报告 → §9.2 模板

阶段 D · 自动修复（用户说「自动修复/清理死代码/去冗余/消除重复」时）
  D1: 打标签 + 定动词 → §10.2 / §10.3（fix-taxonomy.md）
  D2: 过滤 → §10.5 三张表（可自动 / 待人工 / 禁止自动）
  D3: 自动堆逐点改 + §10.6 四项验证（单批 ≤10）
  D4: 人工堆出方案不改码 → §10.8 双视角报告
```

**核心框架**：阻断判定（先）→ 并行深审（中）→ 优化/技术债（后）→ 自动修复（按需）。P0/P1 修复后必走验收循环：修→最小验证→≤3 轮回修→升级人工。

### 1.2 并行分组与依赖关系

| 分组 | 检查项 | 可并行原因 |
|------|--------|-----------|
| **W1 静态规则组**（工具化，互不依赖） | 40 项规则 grep · 敏感文件/lockfile 检查 · 循环依赖/上帝类扫描 · 依赖版本扫描 | 纯模式匹配，只读文件内容，无相互依赖 |
| **W2 语义分析组**（互不依赖，可并行） | 正向数据流追踪 · 逆向数据流追踪 · OWASP 清单过查（§3.4④）· 测试覆盖评估 | 各自独立成结论，结论互不为输入 |
| **W3 Spec 忠实轴**（独立子代理，可并行） | 对照原始需求/spec/issue 逐条核对实现忠实度：功能是否齐全 · 是否夹带未要求改动 · 是否偏离约定行为 | 独立上下文，只接收 diff + 原始需求，**不接收 W1/W2 结果**——避免确认偏误（来源 mattpocock/skills code-review 双轴：Standards 与 Spec 并行互不污染，2026-10-16 吸收） |
| **串行依赖**（必须后置） | 缺陷分级 → 去重聚合 → 技术债量化（DICE/ROI 以问题清单为输入）→ 报告生成 | 每步以上一步产出为输入 |

### 1.3 聚合规则

- 同一 `文件:行号` 被多项检查命中 → **保留最高级别**，规则引用合并（如 `PY-07 + OWASP-A02`）
- W1 命中但 W2 无法语义确认 → 降级标注"待验证假设"（对齐 §三 三分离原则），不定级 P0
- W3 Spec 轴发现「夹带改动/偏离需求」类问题单独归类，不与 Standards 轴缺陷合并去重（两轴发现的问题类型正交）；Spec 轴报「缺功能」时标注来源 `[spec]`
- 每条发现标注置信度：**高**（grep 直击 + 上下文确认）/ **中**（单引擎命中）/ **低**（待验证）
- 分级对齐 §7：阻断类（P0/P1）与可选项（P2/参考）在报告中**分组呈现，不混线**
- **打标签（阶段 B 汇聚时必做）**：每条发现额外标一个 §10 标签（24 标签闭集）+ 主动词（10 动词闭集）；级别定严重度、标签定动作，两者互不替代；同位置多标签按 §10.9 仲裁

**验收循环（P0/P1 修复后必走）**：

```
修复 → 最小验证 → 通过 → Step 9 后置核验
              └→ 不通过 → 回修（≤3 轮）→ 3 轮仍不过 → 停止盲改，回溯根因，升级人工
```

- **验证方式（对应修复目标的最小验证）**：P0 安全漏洞 → 攻击向量测试通过；P1 异常处理 → 异常路径测试 exit 0；脚本修改 → `py_compile` + 最小路径实跑；配置/部署 → 产物打开 + 服务 restart 后探活
- **禁止**：验证不通过却报"已修复"；第 3 轮后继续盲改（回溯根因优先于重试）
- **报告标注**：未闭环的修复在总结中单独列出，不混入"已修复"计数

**阻断判定与批准规则**（吸收 Google eng-practices + GitLab code review 指南）：

- **批准标准**：确定是代码库的整体改进即可批准，不因"不完美"拒绝——可选项（P2/参考）不阻塞结论
- **阻断红线**：P0/P1 存在即不批准；正确性/安全性/设计劣化必须修复；无测试守护的高风险新行为必须补测
- **早停输出**：P0 扫出后立即给出阻断报告（结论 + 位置 + 证据 + 修复方向），不等待优化层完成；用户要全量报告时再走阶段 C
- **不阻断清单**（对齐 software-code-review skill 的 "When Not to Block"）：纯 P3 风格偏好、可写得更"漂亮"但无缺陷的实现、影响范围外的既有问题（转 follow-up issue 不扩大本次范围）、作者已明确接受并跟踪的低风险测试缺口
- **必须阻断清单**：P0/P1、数据迁移/公共 API 形态/安全边界的破坏性变更、合并后修复代价高昂的事项
- **证据门槛**（Finding Proof Gate）：上报 P0/P1 前必须给出最小证明——可达的执行/状态转换路径、失败示例/测试或具体契约不匹配；证据不可知时报告为**待验证假设**（不定级 P0）

**三路分发（审查深度自动分流）**：

| 级别 | 触发条件 | 审查内容 | 预期深度 |
|------|---------|---------|---------|
| 轻量 | 改动 <100 行，无敏感标签 | 静态规则扫描 + 快速人工（跳过 W2 语义组） | 快通道，1 轮 |
| 标准 | 改动 100-400 行，常规业务 | A 阻断判定 + B 并行深审（W1‖W2）+ C 完整报告 | 完整流程 |
| 对抗 | 改动 >400 行，或涉及敏感标签 | 数据流追踪 + 安全专项 + 架构影响 | 最深，W1/W2 + 专项 overlay |

**敏感标签**：`auth` `pay` `credential` `secret` `token` `db` `sql` `schema` `admin` `permission` `upload` `download` `api`

**PR 规模控制**（对齐 Google「100 行合理 / 500 行偏大」+ GitLab「~200 行是好目标」）：≤400 行正常审查；400-1000 行拆分审查（按功能/模块分组，组间并行）；>1000 行拒绝合并必须拆分。一个 PR 只做一件事；重构与功能分离；纯格式化单独 PR。
